# Webhook Delivery Service — System Design

> Filled in round by round. Each section is written only after we agree on it.

## 1. Functional Requirements

**Actors:** Sender (produces events) → **X** (our service) → Receiver (owns a URL). Operator watches X.

**Receiver**
1. Registers a URL + the event types it wants (via the sender's UI, which calls X).
2. Gets back a signing secret generated by X, shown once. Uses it to verify incoming requests.
   - 2b. Can list, update (URL / event types), disable, and delete its endpoints.

**Sender**
3. Publishes events (type + JSON payload) to X. Never talks to receivers, never retries.

**X (our service)**
4. Accepts an event; once it says OK, the event is never lost.
5. Fans out: delivers each event only to endpoints subscribed to that event type.
6. Signs every delivery with the endpoint's secret (HMAC + timestamp).
7. Retries failed deliveries with exponential backoff: 1 attempt + 3 retries.
   - Retry on: timeout, connection error, 5xx, 408, 429.
   - Other 4xx → dead immediately (resending the same payload won't fix it).
8. After the final retry fails, the delivery is marked **dead** and kept, not deleted.

**Operator**
9. Sees events and deliveries with status (pending / delivered / retrying / dead) and each attempt's detail (status code, error, latency, time).
10. Replays a dead delivery, singly or in bulk.

**Out of scope (v1):** user accounts / multi-tenant auth (single API key), per-receiver rate limiting, ordering guarantees, payload transformation, receiver-facing portal, SDKs.

## 2. Non-Functional Requirements

| Quality | Requirement | Design decision it forces |
|---|---|---|
| **Delivery guarantee** | At-least-once. Receiver dedupes on `event_id` → effectively exactly-once processing. | Every event has a unique ID; retries are safe. |
| **Durability** | Once X returns 202, the event survives any crash. In-flight jobs from a crashed worker are picked up again. | Persist before ack; jobs need a lease/timeout so they're never stuck "in progress". |
| **Ack latency** | `POST /events` p99 < 100ms. | Only validate + 1 DB write before replying → delivery is **async** → background workers. |
| **Delivery latency** | Healthy receiver gets the event p99 < 5s (≈ 0.1s save + 1s pickup + 0.5s HTTP, rounded up). | Workers poll at ~1s. |
| **Throughput** | 100k events × 3 endpoints delivered within 5 min. | ~300–1,300 concurrent sends (see §3) → async I/O workers, not one thread per send. |
| **Ordering** | Not guaranteed. | Avoids head-of-line blocking. Receiver dedupes by event ID and refetches state. |
| **Isolation** | A dead receiver must not slow healthy ones. | 5s HTTP timeout · retries stored as `next_attempt_at` (no sleeping workers) · circuit breaker: 10 consecutive failures → pause endpoint 1 min, without burning attempts. |

## 3. Back-of-envelope Estimates

- Deliveries: 100k events × 3 endpoints = **300k**
- Attempts per delivery at 30% failure: 1 + 0.3 + 0.09 + 0.027 ≈ **1.43** → **~430k attempts**
- Rate: 430k ÷ 300s ≈ **1,433 attempts/s**
- Concurrency (Little's Law, in-flight = rate × latency):
  - All attempts 200ms → 1,433 × 0.2 ≈ **287 in flight**
  - Half of failures are 5s timeouts → avg 0.92s → **~1,320 in flight**
- Takeaway: timeouts are 15% of attempts but ~80% of worker time. Timeout length and the circuit breaker are the main capacity levers.
- Expected dead after retries: 0.3⁴ ≈ 0.8% → ~2,400 deliveries → recovered via replay in the demo.

## 4. Core Entities

Courier analogy: address book entry → letter → parcel (letter + one address) → logbook line.

| Entity | Represents | Holds (no columns yet) |
|---|---|---|
| **Endpoint** | A receiver's registered URL | URL, subscribed event types, signing secret, breaker counters, enabled flag |
| **Event** | One thing that happened — **immutable** | event ID, type, payload, received time |
| **Delivery** | One event going to one endpoint | event, endpoint, status (pending / delivered / dead), attempts used, next attempt time |
| **Attempt** | One HTTP try for a delivery — append-only log | delivery, time, HTTP status or error, latency |

```
Endpoint ──┐
           ├──< Delivery >──< Attempt
Event ─────┘
```
- 1 Event → N Deliveries (one per subscribed endpoint, created at fan-out)
- 1 Endpoint → N Deliveries
- 1 Delivery → up to 4 Attempts per round (more after replays)

**Status lives on Delivery, never on Event** — an event can be delivered to A and dead for B at the same time.

**Replay:** Delivery `dead → pending`, `attempts_used` reset to 0, due now. Old Attempt rows are kept as history; a new Attempt row is written when a worker actually tries. Event is untouched, so the receiver's dedupe on event ID still works.

**Not entities in v1:** Sender (single API key), Operator (no accounts), X itself.

## 5. API Design

Rules: path = noun (entity), method = verb, ID → path, filters → query string, actions → `POST /thing/:id/action`. Auth: single API key (`Authorization: Bearer …`).

| Method + path | Caller | Purpose |
|---|---|---|
| `POST /endpoints` | Receiver (via sender UI) | Register URL + event types → returns secret **once** |
| `GET /endpoints` | Receiver | List endpoints |
| `PATCH /endpoints/:id` | Receiver | Change URL / event types, enable / disable |
| `DELETE /endpoints/:id` | Receiver | Remove |
| `POST /events` | Sender | Publish → `202 Accepted` |
| `GET /deliveries?status=&endpoint_id=` | Operator | Dashboard list |
| `GET /deliveries/:id` | Operator | One delivery + all its attempts |
| `POST /deliveries/:id/replay` | Operator | Replay one |
| `POST /deliveries/replay` | Operator | Bulk replay by filter (body: `{status, endpoint_id}`) |

**Register**
```http
POST /endpoints
{ "url": "https://warehouse.example/hooks", "eventTypes": ["order.created", "order.cancelled"] }

201 Created
{ "id": "ep_7", "url": "...", "eventTypes": [...], "secret": "whsec_…", "enabled": true }
```

**Publish**
```http
POST /events
Idempotency-Key: order_555_created
{ "type": "order.created", "payload": { "order_id": 555 } }

202 Accepted
{ "event_id": "evt_42" }
```
- Idempotency key is sender-generated and **stable across retries**; enforced by a DB `UNIQUE` constraint.
- Duplicate key → `202` with the **original** `event_id` (not an error).
- ponytail: same key + different body returns the original; reject with 422 if it ever matters.

**What the receiver gets**
```http
POST https://warehouse.example/hooks
X-Webhook-Id: evt_42
X-Webhook-Timestamp: 1759651200
X-Webhook-Signature: v1=<hex HMAC-SHA256(secret, "timestamp.body")>
{ "id": "evt_42", "type": "order.created", "created_at": "...", "payload": { "order_id": 555 } }
```

**Two hops, two dedupe points**
```
Sender ──retry──▶ X        Idempotency-Key on POST /events   (X dedupes)
X ──retry──▶ Receiver      event_id in every delivery         (receiver dedupes)
```

## 6. Database Schema

Postgres. Four tables, one per entity.

```sql
CREATE TABLE endpoints (
  id                   text PRIMARY KEY,                 -- ep_7
  url                  text NOT NULL,
  event_types          text[] NOT NULL,
  secret               text NOT NULL,                    -- needed in plain form to compute HMAC (encrypt at rest in prod)
  enabled              boolean NOT NULL DEFAULT true,
  consecutive_failures int NOT NULL DEFAULT 0,           -- circuit breaker
  paused_until         timestamptz,                      -- circuit breaker
  created_at           timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE events (                                    -- immutable
  id              text PRIMARY KEY,                      -- evt_42
  type            text NOT NULL,
  payload         jsonb NOT NULL,
  idempotency_key text NOT NULL UNIQUE,                  -- sender retries dedupe here
  created_at      timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE deliveries (
  id              bigserial PRIMARY KEY,
  event_id        text NOT NULL REFERENCES events(id),
  endpoint_id     text NOT NULL REFERENCES endpoints(id),
  status          text NOT NULL DEFAULT 'pending'
                  CHECK (status IN ('pending','delivered','dead')),
  attempts        int  NOT NULL DEFAULT 0,
  next_attempt_at timestamptz NOT NULL DEFAULT now(),    -- also the lease
  created_at      timestamptz NOT NULL DEFAULT now(),
  UNIQUE (event_id, endpoint_id)                         -- re-running fan-out can't double up
);
-- only the to-do pile is indexed; delivered rows (~99%) stay out of it
CREATE INDEX deliveries_due ON deliveries (next_attempt_at) WHERE status = 'pending';

CREATE TABLE attempts (                                  -- append-only log
  id           bigserial PRIMARY KEY,
  delivery_id  bigint NOT NULL REFERENCES deliveries(id),
  attempted_at timestamptz NOT NULL DEFAULT now(),
  status_code  int,                                      -- null on timeout / connection error
  error        text,
  duration_ms  int NOT NULL
);
CREATE INDEX attempts_by_delivery ON attempts (delivery_id);
```

**Worker claim (lease) — atomic, committed before the HTTP call**
```sql
UPDATE deliveries d SET next_attempt_at = now() + interval '30 seconds'
WHERE d.id IN (
  SELECT d2.id FROM deliveries d2
  JOIN endpoints e ON e.id = d2.endpoint_id
  WHERE d2.status = 'pending' AND d2.next_attempt_at <= now()
    AND e.enabled AND (e.paused_until IS NULL OR e.paused_until < now())
  ORDER BY d2.next_attempt_at
  LIMIT 50
  FOR UPDATE OF d2 SKIP LOCKED
)
RETURNING d.*;
```
- `next_attempt_at` doubles as the lease: worker dies → row is due again in 30s, picked up by the normal query. No extra column, no recovery code.
- Lease (30s) > HTTP timeout (5s) + margin.
- A worker slower than its lease can cause a duplicate send — acceptable under at-least-once; receiver dedupes on event ID.

**After the send:** success → `status='delivered'`, reset endpoint `consecutive_failures`. Retryable failure → `attempts+1`, `next_attempt_at = now() + backoff(attempts)`, or `status='dead'` if attempts = 4. Always insert an `attempts` row.

## 7. High-Level Architecture

```
                         ┌──────────────────────────────┐
 Sender ─POST /events──▶ │ API server                   │
        ◀──202─────────  │  1 txn: INSERT event         │
                         │         INSERT deliveries×N  │──┐
 Receiver UI ─/endpoints▶│  (fan-out lives here)        │  │
                         └──────────────────────────────┘  │
 Dashboard ─/deliveries, /replay ──▶ (same API server)     │
                                                           ▼
                                                  ┌──────────────────┐
                                                  │ Postgres         │
                                                  │ = store + queue  │
                                                  └──────────────────┘
                                                     ▲   claim (SKIP LOCKED lease)
                                                     │   record result / attempt
                                                  ┌──┴───────────────┐
                                                  │ Workers (async)  │──signed POST──▶ Receivers
                                                  │ ~300–1,300 in    │◀──2xx / 5xx / timeout
                                                  │ flight           │
                                                  └──────────────────┘
```

| Box | Job |
|---|---|
| **API server** | Validate, dedupe on Idempotency-Key, fan-out + save in **one transaction**, reply 202. Serves endpoint CRUD and dashboard reads/replays. |
| **Postgres** | Source of truth **and** the queue (partial index + `SKIP LOCKED` lease). |
| **Workers** | Loop: claim batch → sign (HMAC) → POST with 5s timeout → record attempt → delivered / backoff / dead → update circuit breaker. Async I/O so one process holds hundreds of sends. |
| **Dashboard** | UI over `GET /deliveries`, `GET /deliveries/:id`, replay endpoints. |

**Crash story:** API dies before commit → sender gets no 202 → retries with same Idempotency-Key. API dies after commit → event + deliveries already durable. Worker dies mid-send → lease expires in 30s → another worker picks it up. Nothing is lost at any point.

**Why no Kafka/RabbitMQ:** ~1.4k attempts/s is well within one Postgres; one system to run, transactional fan-out for free, and the dashboard queries the same tables the workers use. ponytail: Postgres-as-queue, move to a broker if sustained load outgrows one primary.

## 8. Deep Dives (retries, signing, idempotency, crash recovery)

### 8.1 Backoff schedule
`wait(n) = 10s × 3ⁿ × random(0.8, 1.2)` for retry n = 0, 1, 2.

| Try | Base wait | Time since first try (no jitter) | With ±20% jitter |
|---|---|---|---|
| 1 | — | 0s | 0s |
| 2 | 10s | 10s | 8–12s |
| 3 | 30s | 40s | 32–48s |
| 4 | 90s | 130s | 104–156s |

- Rides out a 60s outage: even the earliest final try (~104s) lands after recovery. The circuit breaker is the second net (paused time burns no attempts).
- Jitter breaks the thundering herd: 1,000 same-second failures retry over ~4s (~250/s), not all at once, and never re-synchronise.
- ±20% instead of full jitter (`random(0, wait)`, per AWS) so the final try can't land inside a short outage.
- Cost: a thrice-failed delivery takes ~2 min. Fine for webhooks; healthy p99 is still < 5s.

### 8.2 Signing _(not drilled yet — revisit)_
- `signature = HMAC-SHA256(secret, "<timestamp>.<raw body>")`, sent as `X-Webhook-Signature: v1=<hex>` with `X-Webhook-Timestamp`.
- Receiver recomputes and compares with a **constant-time** compare.
- **Replay protection:** receiver rejects timestamps older than 5 min. The timestamp is *inside* the signed string, so an attacker can't swap in a fresh one without breaking the signature.
- New timestamp + signature on every attempt (a retry is signed fresh).
- Same scheme as Stripe (`t=…, v1=…`).

### 8.3 Demo proof (the checker)
**Fake receivers** (3 endpoints) per request:
1. Verify signature → count bad ones.
2. Log to `received` (every arrival, duplicates included).
3. Randomly: return 500 **without** processing (~30%), or time out, or **process then return 500** (simulates a lost ack → forces real duplicates).
4. Otherwise `INSERT INTO processed (event_id, endpoint) ON CONFLICT DO NOTHING` → return 200 (idempotent receiver).

**Run:** publish 100k events → optionally kill X mid-run and restart → kill one receiver ~60s (breaker demo) → wait for drain → bulk replay dead → wait for drain.

**Checker:** expected = published event IDs × subscribed endpoints (300k pairs).
```
expected pairs        300,000
processed pairs       300,000   → lost: 0
duplicates received     ~4.8k   → at-least-once retried lost acks
processed twice             0   → receiver idempotency absorbed them
bad signatures              0
dead → replayed         ~2.4k   → all delivered after replay
```
Headline line: **duplicates received > 0, processed twice = 0.** That's "exactly-once = at-least-once + idempotency", shown with numbers.

## Decision Log
| # | Decision | Why | Rejected alternative |
|---|----------|-----|----------------------|
| 1 | X generates the secret, not the receiver | Guarantees strong, unique secrets | Receiver-supplied secret |
| 2 | Retry cap = 1 + 3 retries, then dead + manual replay | Keeps the demo simple; replay closes the gap (~0.8% dead at 30% failure rate) | Retrying for days like Stripe |
| 3 | Non-retryable 4xx → dead immediately | Same bytes will fail the same way | Retrying every error |
| 4 | At-least-once + receiver idempotency | Exactly-once is impossible over a network (lost 200 OK) | Claiming exactly-once |
| 5 | No ordering guarantee | Ordering = head-of-line blocking per endpoint | Per-endpoint FIFO |
| 6 | 5s timeout + `next_attempt_at` + circuit breaker | Timeouts dominate worker time; dead receivers must not starve healthy ones | Per-endpoint concurrency caps (throttle healthy receivers) |
| 7 | Status on Delivery, not Event; Attempts append-only; Events immutable | One event has many independent outcomes; history must survive replay | Single status on Event |
| 8 | Replay resets the attempt budget | A replay is a deliberate fresh start by the operator | Replay gets only one try |
| 9 | `Idempotency-Key` on `POST /events`, enforced by DB UNIQUE | Sender retries after a lost 202 would create duplicate events | App-level "check then insert" (races) |
| 10 | Replay as `POST /deliveries/:id/replay` | Replay is an action, not a field update | `PATCH status=pending` |
| 11 | `UNIQUE (event_id, endpoint_id)` on deliveries | Re-running fan-out after a crash can't create duplicates | App-level checks |
| 12 | Partial index on pending deliveries | Index stays tiny as delivered rows pile up | Index on `status` alone (low cardinality) |
| 13 | Lease via `next_attempt_at` + `SKIP LOCKED`, commit before HTTP | Crash recovery for free; no long-held transactions | Separate `locked_until` column; holding a txn during the send |
| 14 | Fan-out inside `POST /events`, same txn as the event insert | Atomic: never an event without its deliveries | Async fan-out step + `fanned_out_at` sweeper (switch when endpoints per event get large) |
| 15 | Postgres is the queue | 1.4k/s fits; one system; transactional fan-out | Kafka / RabbitMQ / Redis |
| 16 | Backoff 10s × 3ⁿ with ±20% jitter | Survives a 60s outage; breaks retry stampedes | Fixed waits (thundering herd); full jitter (final try may land mid-outage) |

## 9. Build Plan

Stack: TypeScript · pnpm · Express 5 · `pg` · Neon (Postgres) · Railway. Tests: built-in `node:test` via `tsx --test`.
Deploy shape: one Node process running `api` + `worker` modules; worker sleeps when nothing is pending and is woken through a `WorkSignal` interface (in-memory today, LISTEN/NOTIFY or polling if split later). Lets Neon scale to zero (free tier: 100 CU-hours/month).
